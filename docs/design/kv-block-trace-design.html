A01 / DECISION设计结论

保留现有 KVTrace → JSONL → tools/kv_block_trace.py 路径，在它上面补全身份、因果关联和边界证据。第一阶段交付可回放的链路，后续把 L1 行为校验、语义摘要和内容校验接到同一事件流。

  1. 物理块号必须带作用域与代次。单独的 block_id 无法区分不同引擎、rank、存储池和重用后的块。所有跨组件事件携带同一个分配身份，搬运事件显式关联源块和目标块。
  2. 区分调度意图、实际入参和设备完成。Scheduler 认为写哪一块、Worker 真正传给算子的 slot，以及数据何时可读，要分别记录。图模式下 Python 返回不能代替设备完成。
  3. 行为证据与内容证据分别判断。L1 检查归属、有效范围和顺序；语义摘要检查是否属于同一前缀；checksum / snapshot 检查字节在何处变化。单个 hash、token ID 或状态机均不足以证明 KV 正确。
  4. 无证据时输出“不完整”。未适配路径、丢事件、缺少起始快照、并发写入和缺失远端 trace 都必须显式展示。禁止把“未观察到异常”转换成“未发生污染”。

第一条闭环：v1 runner + 稠密 PA / MLA 的已适配布局 + MooncakeConnectorV1。先贯通 P 端生成、传输、D 端首次读取、dummy 干扰与块复用，再扩展 CPU offload / AscendStore。Trace 默认只观测，不修改 slot、清空缓存、改变采样或自动阻断推理。

PPT 状态图存在演进差异：第 13 / 17 页存在从 UNKNOWN 任意 offset 起写或 SEALED_LOAD 从 0 续写的表达，第 19 / 24 页又强调从 0 开始与密封后禁写。本设计以明确的 ALLOC / INVALIDATE / LOAD 完成事件消除歧义：不能仅凭 offset=0 推断“合法重用”；读操作不能把 UNKNOWN 自动升级成已加载。

PPT 的“约 1% 开销”“累计 48h”和 msprobe 解耦收益属于参考方案自述。本设计没有复测这些结果，也不将其用作全链路 trace 的性能承诺。原始 PPT 保留在工作区，不复制到仓库。

A04 / END-TO-END CHAIN链路与组件边界

收集器在每个进程内持有独立实例，热路径只提交紧凑记录，后台做序列化和落盘。无需独立服务、数据库或跨节点同步日志 RPC。不同节点文件离线汇总，保持 host / actor / writer 身份，不靠文件名或机器时钟推断关联。

如果后续接入 PPT 的 runtime processor，只增加 on_incident(context) 与不可变 snapshot 引用的适配层，复用检测 / report / dump 队列；不再建第二套报告目录或独立控制面。本基线没有该 processor，首阶段由 trace 自己输出 incident。

A05 / IDENTITY块身份、内容身份与映射

对象建议身份含义
运行 / 引擎实例run_id + engine_instance_idrun_id 由 P/D 共用；engine_instance_id 在每次启动生成，绑定配置中的 engine_id、host、DP rank，避免重启串线。
分配身份pool_instance_id + block_id + alloc_epoch由实际 BlockPool 产生。新用途领取该物理槽时 epoch++；prefix touch 继续旧 epoch。group 是使用视图，不能凭 group 另造同一池的分配事实。
设备存储片段worker_instance_id + storage_region_id + shard + block_id + alloc_epochshard 包含 TP/PP/CP 坐标。region 注册时绑定 layer、K/V 或 MLA 组件、group 与布局。共享 tensor / view 关联同一 backing region，防止跨层别名被当成独立存储。
请求引用request_key + group_id + logical_block_index + mapping_revisionrequest_key 含 engine 实例和原始 request_id。一个物理块可有多个合法前缀读者，记录 owner 集合与可写范围。
内容版本content_revision + valid_ranges + provenance_id每个 region / shard 上的已完成写入改变 revision；跨设备搬运只建立来源关系，不要求两端 revision 数值相同。
内容语义prefix_digest + semantic_context_id独立于物理块，覆盖 token 前缀、位置 / RoPE 配置、模型 revision、LoRA、多模态内容标识、cache salt 等适用上下文。相同当前 token 不代表相同 KV。
搬运 / 操作transfer_id + attempt_id + segment_id；op_id跨 P/D 显式透传。一次搬运可以一对多、多对一；segment 描述 layer、组件、token 区间、head/shard、源目标 byte range。

epoch 的具体产生规则：在 BlockPool.get_new_blocks 成功领取并完成旧 cache 绑定清理后递增；在 touch 命中旧前缀时不递增。free_blocks 降引用但可能保留 hash / 字节，不能自动 invalidate。单独的 evict / reset 记录语义绑定失效，直到重新分配才进入新 epoch。[S9]

Scheduler → Worker 的上下文传播

扩展调度消息的可选 trace 字段，包含 scheduler_instance_id、step_id、mapping_revision 和变更块的 (pool, block, epoch)。Worker 记录收到、应用、构建实际入参三个事件。进程本地变量无法跨 IPC 保证关联；需要小范围上游 SchedulerOutput 协议扩展，或经验证的等价序列化扩展点。首版已核对指定 commit 的多进程 MessageQueue 使用 pickle，并验证真实 SchedulerOutput dataclass 的附加上下文在 Windows spawn 跨进程后保留，因此在这一明确通道使用附加属性兼容实现；其他通道缺少上下文时记录 trace.gap。正式上游字段扩展仍是长期方案。[S10]

Allocator block 与 kernel block

仅对已确认的连续稠密布局：B_alloc % B_kernel = 0
scale = B_alloc / B_kernel
allocator_block = floor(kernel_block / scale)
allocator_offset = (kernel_block % scale) × B_kernel + kernel_offset

例如 allocator block 大小 128、kernel block 大小 32，kernel block 29 的 offset 7 对应 allocator block 7 的 offset 39。保留两套原始坐标和转换依据。PCP/DCP、压缩块、NZ、异构 block size 必须经过各自 layout adapter，不能套用上述公式。null block 的身份从注册布局读取；slot=-1 是 padding。基线硬编码排除 block 0 的规则需要转为显式配置。[S5] [S13]

A06 / LIFECYCLE生命周期与可验证不变量

每个实际存储片段维护三类信息：归属（free / referenced / cached，以及传输中的持有关系）、有效内容（empty / partial / sealed / invalid）、在途操作（write / load / copy 的 issued、ready、failed）。对照表在 Scheduler、Worker 分别维护，通过事件比对，不由一个“全局可变对象”跨进程共享。

事件状态变化允许条件 / 检查
ALLOC / ACQUIRE新 epoch 从 empty 开始；请求取得引用。ALLOC 与共享 ACQUIRE 分开。新用途分配不得与旧 epoch 的真实读写 / 传输持有重叠；trace 只报告，不替业务管理引用。
PREFIX_ATTACH增加 reader；保留 epoch、已就绪有效范围与内容来源。匹配语义摘要、上下文及已提交范围。前缀命中不发生数据搬运，不能伪造 LOAD。
WRITE_ISSUED / READYissued 记录意图；ready 后更新对应 layer / component 的 valid_ranges 与 revision。稠密顺序写从 n=valid_len 开始，允许一次写多个 slot；全块 n=B 时为 sealed。必须匹配 epoch、owner、mapping revision 和实际 token 范围。
LOAD_ISSUED / READY仅 ready 后发布收到的有效区间；尾块仍是 partial。声明源块身份、目标 epoch、有效长度及全部必需 segment。不能把“传输请求入队”当作完整 block 已就绪。
READ不改变内容状态。需要的 cache 范围已 ready，且属于正确语义前缀；当前 Q 的 direct K/V 与历史 cache 的读范围分别描述。未知 / 丢失状态为 inconclusive。
COPY / CoW目标是新分配身份，继承被复制范围的 provenance；后续写独立演进。源在复制期间可读，目标独占，copy ready 后继承有效性。只复用 tensor view / 引用时记录 alias，不伪造字节 copy。
RELEASE / EVICT / INVALIDATErelease 降引用；evict 移除 cache 绑定；invalidate 清除对应有效范围。release 不等于内容清零。zero 操作也只是字节变化，不能把清零后的数据视为有效 KV。记录 request 完成、抢占、滑窗淘汰、失败等原因。
SPEC_COMMIT / ROLLBACK区分 written / committed 范围；拒绝 token 的写入可物理残留。只允许在明确标记为 uncommitted 且已回收的尾部重写。没有 speculative adapter 时，不对 offset 重复写做确定判错。

L1 的判定边界

稠密 PA 可用 valid_len 压缩连续有效区间，但必须按 layer / backing region 维护，不能第一层写完就把所有层标记 ready。跨流读取需要已记录的 wait / completion 依赖；同流操作可依据 stream FIFO 推导 ordered_after_write，仍需与“host 已确认 ready”区分。

对传入 attention 的 cache read-set 检查 requested_ranges ⊆ ready_ranges。某些 FIA 路径直接读取完整 cache，另一些融合路径同时使用 current K/V；不能一律使用 seq_len − query_len，也不能一律使用完整 seq_len。由 backend 根据最终调用参数返回 read-set。当前 _get_fia_params 已有不同 attention state 的分支。[S6]

有效证据的前提：epoch 不匹配、读未完成、密封区被覆盖等结论，只有在对应生命周期与操作事件完整、布局已适配时才是 violation。缺少钩子时记录 coverage gap；原始 slot 指向合法地址但计算出的 K/V 值错误，需要内容证据和标杆比较。

A07 / EVENT CONTRACT事件契约、版本与因果顺序

现有 JSONL 为 schema v1。扩展使用 schema v2，不改变已有事件的含义；reader 同时读取 v1/v2，将 v1 未知的 epoch、完成语义和覆盖范围保留为 unknown。示例与新增字段均为设计目标。

顺序依据为：同 writer 的 sequence、调度 dispatch→apply、transfer offer→各 attempt / segment、设备 stream 依赖、完成→首次读。离线工具构建这些边组成的 DAG。wall time 只用于近似展示；跨机时钟倒退不改变因果判断。两个无依赖事件保留“并发 / 未知顺序”，不强行给出先后。

A09 / TRANSFER INTEGRITYPD 和外部存储的闭环

PD 检查点

  1. P 计算完成：按 layer / component 的设备完成依赖观察 KV，记 produced 摘要。源请求、token 区间、epoch 和 shard 固定。
  2. P 提供传输：在现有 delayed-free / 保活机制仍持有源块时建立 export manifest 与 transfer_id；可选再次取 export 摘要，检查计算后到搬运前是否变化。
  3. D 提交接收：关联双方 request_key，并冻结本次 attempt 的源目标映射。每个 segment 记录实际传输范围；同一请求重试产生新 attempt，不能复用上一轮成功状态。
  4. 传输字节完成：Mooncake 同步 read 成功仅发布 bytes_complete。如果需 gather、transpose、NZ 或 TP 变换，再记录 layout_ready 的设备事件，不能用 host 返回提前判 ready。
  5. D 发布与首次读：必需 segment 全部完成，且目标 epoch 仍匹配后发布 valid_ranges；在 attention 首次读取前观察 consume 摘要。取消、失效或旧 epoch 的迟到 completion 不得纳入新块状态。
  6. 源端释放：记录真正的 block.release 与原因。worker_finished、超时清理、ACK 和 release 分别表达，避免把完成通知误作数据校验成功。

若源端 checksum 需要设备计算，不新增一条会阻塞业务的强制同步 RPC。先在原有计算 stream 上排队产生结果，由后台在完成后落盘，通过 transfer_id 离线关联；只有在诊断模式明确选择冻结快照时增加必要依赖，并记录对时序的扰动。

不同 TP / PP / 布局的比较

跨端比较依据 (semantic_context, logical_token_range, global_layer, component, global_head_or_latent_range) 对齐；不能直接比较 P block 37 与 D block 12 的原始内存 hash。相同字节布局做 bitwise hash；重排后按 canonical layout 比较；量化 / 转码路径验证转换契约和 scales，以声明的数值容差评估。未注册转换器就返回 not_comparable。

manifest 同时保存分配块、kernel 子块、真实传输字节数、必需片段集合。sum(bytes) 只能发现总量异常；必须检查区间并集与期望区间一致，识别重复传片与缺失片段。部分 tail 的无效 bytes 不参与语义完整性判定。

CPU offload / Store

每次 put 绑定 store_instance_id + object_key + object_generation，附布局、有效范围、来源与摘要。get 记录查询键、命中 generation、加载目标 epoch 和 load ready。检测链为 device_before_store → stored → loaded → device_after_load；cache hit 只说明索引命中，不说明对象内容正确。

已有存储格式不能带 metadata 时，诊断 sidecar 必须与对象 generation 原子关联或验证前后版本一致；不能只按可复用的 object_key 建旁路字典。拿不到版本 / 摘要的后端只具备搬运 trace，不宣称内容闭环。失败、取消、缓存驱逐以及压缩方式变更均留下失效事件。

A10 / EVIDENCE内容校验与现场保存

证据层回答的问题限制 / 成本
生命周期 / L1谁拥有块？是否先写后读？是否读了旧 epoch 或无效范围？依赖完整 hooks 与已适配状态语义；无法证明正确 offset 上的值正确。

安全的快照时序

检测命中后，在明确的写完成依赖之后，将选中有效区间复制到预分配的独立 snapshot buffer。源块在 copy 完成前必须通过现有持有机制或受控 copy fence 避免重用；随后 D2H 到独立 pinned buffer。队列任务持有私有 buffer 和 completion event，只有 D2H ready 后才能读取，落盘后释放配额。

若只能实现同步 D2H，则作为显式 deep 模式，记录同步耗时。普通 trace 模式不得临时强加全设备 synchronize。没有能力建立原子快照或存在未观测并发 writer 时，记录 snapshot_consistency=unknown；这份数据只能说明某个观察窗口出现变化。

冻结策略与报告

触发来源包括 L1 violation、语义 / checksum mismatch、外部 detector、手工 request / block 选择。保存事前环形事件窗口、触发点、短事后窗口、相关 owners / transfers、所选快照和完整性摘要。同一 block epoch 与同类 incident 在冷却窗口内合并，避免复读问题反复 dump。

资源上限必须可计算

M_total ≈ N_pool_entries × bytes_alloc_state
　　　　+ N_tracked_regions × bytes_region_state
　　　　+ N_request_refs × bytes_reference
　　　　+ event_ring_bytes + in_flight_snapshot_bytes
trace_disk_rate ≈ events_per_second × mean_serialized_event_bytes

示例预算而非实测：若 100,000 个跟踪条目用 64 字节紧凑结构，裸数据约 6.1 MiB；Python dict/set 的对象开销需另计。100,000 blocks × 128 slots × 4 字节 token ID 约 48.8 MiB；若错误地按 80 层重复存储则约 3.8 GiB。L2 优先保存块级摘要和按需 token 窗口，不复制每层 token 阵列。

建议首轮实验上限：每进程 event ring 64 MiB、私有 snapshot 总预算 64 MiB、单 incident 1 GiB、run 目录 10 GiB、磁盘预留 5 GiB。都是可调初始值，需按 rank 数和实际数据量确认；磁盘预算按文件系统共享，多个进程通过目录级配额协调，不能各自以为还有同一份空闲空间。

失效情况行为
队列满 / ring 覆盖不阻塞推理；保留独立 gap 计数与丢失序列范围。受影响状态降为 unknown，直到完整 checkpoint 恢复。
磁盘不足 / 写失败停 dump，保留可写的最小 incident；若日志也不可写，输出进程日志和计数器。报告标为 incomplete，禁止静默当作成功。
writer 截断 / 进程退出有限时间 flush，保存 stop / cutoff；crash 可缺尾部 stop，由 collector 标记异常结束。partial JSONL 尾行可跳过但计入损失。
observer 异常隔离记录错误，保留原模型异常和返回值；未安装或已失效 hook 在 manifest / 健康记录反映。
过量 incidents按 block epoch、类别和时间窗口去重；记录 suppressed 数量。已冻结证据不因普通轮转而被删。

实际排查步骤

  1. 先看 manifest、gap 和 capability，确认问题路径有证据。以 engine instance + block + epoch 定位，不只搜裸 block_id。
  2. 从异常 request 展开其物理块，再包含同块的共享 owners、独立 dummy span、所有搬运；保持“关联上下文”与“同一请求别名”两种边。

  4. 对齐 produced、export、layout_ready、consume 的有效范围摘要，得到首次差异窗口；证据缺失就停止在该窗口，不跳跃归因。
  5. 按可疑 token / block 做多层快照与 teacher-forced 标杆比较，缩小到 layer / component，再进入算子或通信诊断。

验证记录必须能复查

先跑 schema / 状态回放 / CLI 的 CPU 测试，再在目标 Ascend 环境验证 v1 eager、graph、PD 和对应 connector。每条结论保留：精确 commit、实际模块 __file__、启动命令、trace 配置、拓扑、触发用例、关键事件 ID、device completion 证据和输出差异。源码修改、安装包、实际加载模块分开记录。

性能测量至少比较 off、当前实现、拟 trace、check、deep：吞吐、TTFT/TPOT 的 p50/p99、CPU、RSS/NPU 内存、D2H bytes、日志速率、丢事件和 snapshot 停顿。先 warmup，再做同一 workload 交错 A/B。建议把 off 的变化限于测量噪声、trace 模式吞吐与 p99 延迟劣化不超过 2% 作为首轮目标；这是待验证目标，不能据 PPT 的约 1% 直接宣布达标。check/deep 单列成本。

退出条件：选定 P0/P1 配置可还原完整生命周期，故障注入定位到对应第一条失败边，正常边界无误报，未覆盖路径不会给出安全结论。更大范围的“全链路”必须在 P2/P3 逐项验收后更新 capability。当前分支交付设计、P0 初版及限定 NPU 验证；详见 kv-block-trace-validation-20260929.md。完整 P0 checkpoint、P1 内容闭环、NPU 性能与长稳实验仍待完成。
