## 摘要（可选）

*给不会通读全文的读者的一段自洽总结：哪里有问题、你提议怎么改、用户会看到什么变化、代价是什么。三到五句话。*

**注：超过两屏的 RFC 建议必写。评审者通常靠这一节做初步判断；不要在这里引入只在后文才定义的新术语。**

> **写作要求**：
>
> - 用一两句话说明问题，用用户或运维人员能听懂的说法。
> - 说明提议的改动和实现机制，不展开实现细节。
> - 说明主要收益和主要代价（性能、内存、兼容性或维护成本）。
> - 不要把「动机」或「设计」整节复述一遍，也不要把注意事项藏到文档最后。

**示例**：

> 混合模型要求所有 KV Cache group 的 page size（字节数）一致，因此核心层不得不按层数重新切分 group、填充 page、抬高 block size。本 RFC 去掉这条规则：KV Cache 池改为一组等大的 large page，每个 page 同一时刻只属于一个 group。分组随之简化为「每个 `KVCacheSpec` 一个 group」，kernel 沿用上游寻址方式。容量与主干版本相差控制在 1% 以内；动机是简化代码，而不是提升容量。

## 动机（必选）

*这个 RFC 为什么存在。描述现状、现状哪里不对，以及为什么现在值得解决。*

**注：本节对应 RFC issue 模板中的 `Motivation.` 字段。若评审者不认同问题本身，后面的每个设计决策都会被质疑，所以问题必须具体且有证据。**

> **写作要求**：
>
> - 描述**现状**：当前代码是怎么做的，链接到相关文件、类或上游代码。
> - 描述**问题**：具体的限制、故障现象或代价。尽量给出可复现的例子（模型、硬件、batch size、命令）。
> - 量化代价：性能数据、内存开销、不支持该能力的模型数量、维护成本，或附链接的用户反馈。
> - 说明**为什么是现在**：哪个即将到来的需求、上游变更或路线图条目让现状无法继续。
> - 区分事实与推测。未验证的假设要显式标注，它们会在后文变成待决问题。
> - 本节不要提出方案。

**示例**：

**现状。** `KVCacheManager` 断言所有 KV Cache group 的 page size（字节数）一致（`assert len(page_sizes) == 1`），模型通过三种方式满足该约束：按层数分组、抬高 block size、填充 page。

**问题。** 分组依据是字节算术而非模型结构。Kimi-Linear-48B 在 TP4 下（20 个 KDA 层、7 个 MLA 层）单个 KDA state 为 561,152 字节；为对齐 MLA 的 page，block size 被抬到 512 token，每个 KDA state 被填充 5.1%。模型只有两种 KV Cache，却实际运行四个 group。

| 证据 | 数值 | 来源 |
|------|------|------|
| KDA state 填充比例 | 每个 state 5.1% | `Kimi-Linear-48B` 在 `TP4` 下的配置 |
| DSV4.1-Flash 分组计划变化 | 7 个 group → 9 个 group | indexer 精度从 fp8 改为 mxfp4，见 #62100 |
| 该绕过方案引入的新概念 | `UniformTypeKVCacheSpecs`、`hash_block_size`、`prefix_match_unit` | `vllm/v1/core/kv_cache_utils.py` |

**为什么是现在。** 本版本要引入两个混合模型，每个都需要在分组启发式里再加一个特例。同时分组逻辑正在改为可插拔（#62100），这把启发式移出核心层，却保留了迫使启发式存在的「等 page size」规则。

## 目标与非目标（必选）

*提案的边界。目标是 RFC 承诺并对之接受评审的内容；非目标是有意排除的内容。*

> **写作要求**：
>
> - 目标写成可检验的陈述（「所有可前缀缓存的 group 共用一个 block size」），不要写成动作（「改进设计」）。
> - 明确列出非目标，尤其是评审者本会以为已包含的那些。
> - 若某目标只部分达成，说明哪部分达成、哪部分推迟，并给出后续 issue。
> - 保持简短。若某个目标没有任何设计决策为其服务，就删掉它。

**示例**：

| 目标 | 非目标 |
|------|------|
| 每个 `KVCacheSpec` 一个 KV Cache group，同 spec 的 draft 层并入目标模型的 group | 提升 KV Cache 容量；容量允许有界损失 |
| 所有可前缀缓存的 group 共用一个 block size，使 block hash 在任何 group 中都代表同一段 token | 新的驱逐策略；缓存 block 继续使用 LRU |
| 不再填充 page、不再因字节对齐抬高 block size、不再需要 sub-block 哈希 | 修改 attention kernel（仅允许 64 位偏移类改动） |
| kernel、slot mapping、block table 保持上游形态 | 多机或多租户的缓存共享 |

## 提议的改动（必选）

*设计本身。这是 RFC 的主体，也是评审者据以实现的章节。*

**注：本节对应 RFC issue 模板中的 `Proposed Change.` 字段。先讲整体形态，再落到接口与算法。无法被拆解为一串具体决策的设计，还不够形成 RFC。**

> **写作要求**：
>
> - **先给总览**：用 Mermaid 或 ASCII 图给出改动后的端到端流程，并在图下编号解释每一步。
> - **详述设计**：逐个覆盖受影响的模块、其职责以及具体改动。写出真实的文件、类和函数名。
> - **接口与配置**：给出完整的对外界面（函数签名、请求字段、CLI 参数、配置项）。在 vLLM Ascend 中，用户可见配置应放在 `--additional-config` 下的类型化配置键中；除非确实无法避免，不要新增环境变量，新增时必须给出充分理由。
> - **数据结构**：对本 RFC 引入的每个结构或接口给出字段表。
> - **关键算法**：对任何不直观的计算给出伪代码或步骤列表，并说明复杂度与边界情况。
> - **与既有特性的交互**：ACLGraph、量化、专家并行、PD 分离、投机解码和前缀缓存都会约束设计，说明它们与本改动叠加时的行为。
> - **与上游的关系**：说明实现方式是 patch、基于继承的扩展，还是向上游贡献；若是 patch，给出长期计划。

**示例**：

**总览。** KV Cache 池变成 `N` 个大小为 `S` 字节的 page。每个 page 同一时刻只属于一个 group，由该 group 按自身大小切分为 block。

```text
      request ──► planner ──► 每个 KVCacheSpec 一个 group
                     │
                     ├── block size  B（所有可前缀缓存 group 共用）
                     └── page size   S（各 group block size 的公倍数）

      pool: [ page 0 ][ page 1 ][ page 2 ] ...
               │           │          │
             KDA grp     MLA grp     free ──► 可被任意 group 取用
```

1. **规划**：planner 为每个不同的 `KVCacheSpec` 建立一个 group，并计算公共 block size `B` 与 page size `S`。
2. **分配**：group 优先从自己已持有的 page 上取空闲 block；否则取一个无缓存内容的空闲 page；再否则驱逐自身 LRU 缓存 block 或最旧的空闲 page。
3. **寻址**：group 的 block `b` 起始于字节 `b × block_bytes`，对应 kernel row 为 `b × R`，无需查找表。

**接口。**

| 接口 | 改动 | 说明 |
|------|------|------|
| `KVCacheSpec` | 不变 | 分组粒度从 page size 变为 spec 本身 |
| `KVCacheManager.allocate_slots` | 新增 `(group_id, block_id)` 寻址 | block id 仅在 group 内唯一 |
| `--block-size` | 复用 | 显式指定的值在可行时原样使用 |

**交互。** 前缀缓存按 block 粒度计算哈希，因此移除 `hash_block_size` 与 `prefix_match_unit`；ACLGraph 按 block size 各捕获一次；PD 分离要求各 rank 几何一致，启动时断言校验。

## 影响与风险（必选）

*这项改动的代价以及可能出错的地方。评审者据此判断收益是否值这些风险。*

> **写作要求**：
>
> - 覆盖适用的维度：性能、内存、兼容性（模型、硬件、配置、已保存状态）、维护与评审成本、测试成本、安全。
> - 对每个风险给出发生可能性、可观测现象和缓解措施。「持续观察」不算缓解措施。
> - 有实测数据时量化性能与内存影响，并写明测得该数据所使用的硬件与负载。
> - 若改动对用户可见，说明是否需要 release note fragment，以及既有用户会遇到哪些行为变化。

**示例**：

| 维度 | 影响 | 风险 | 缓解措施 |
|------|------|------|------|
| 性能 | kernel 寻址与 slot mapping 不变 | 低 | 热路径无改动；用 ACLGraph 基准验证 |
| 内存 | 已验证模型上容量与主干版本相差 1% 以内 | 中：混合 page size 下的尾部浪费 | page size 受「按需求加权浪费不超过 2%」约束，并在启动时断言 |
| 兼容性 | 配置与已保存的 KV Cache 状态不受影响 | 中：自定义 `SupportsKVCacheGrouping` 实现会失效 | 旧分组路径通过迁移开关保留一个版本 |
| 维护成本 | 从核心层移除四处特例 | 低 | 只剩「每个 spec 一个 group」这一条规则需要维护 |
| 测试 | planner 与 allocator 新增单测；混合模型 E2E | 中：混合模型覆盖较薄 | 在 `tests/e2e/models/configs/` 中补充 Kimi-Linear 与 DSV4.1-Flash |

## 备选方案（必选）

*被否决的方案及否决原因。这一节是 RFC 与普通 patch 的区别所在。*

> **写作要求**：
>
> - 把**维持现状**也作为一种备选方案，并说明它为何不再可接受。
> - 每个方案给出思路、优点、缺点和被否决的具体理由。
> - 不要列举稻草人。若某方案看起来可行，说明是什么证据排除了它。
> - 若是推迟而非否决，说明日后在什么条件下可行。

**示例**：

| 备选方案 | 优点 | 缺点 | 未采用原因 |
|------|------|------|------|
| 保留等 page size 规则，仅把分组改为可插拔（#62100） | 改动小，无需重写 allocator | 每个模型或平台都要维护自己的启发式，填充依旧存在 | 只是转移复杂度，没有消除复杂度 |
| 单个 group 内允许逐层 page size | 分组计划极其简单 | kernel、哈希等所有组件都要处理异构 page | 影响面远大于它替代的分组代码 |
| 每个 group 独立 KV Cache 池 | 归属简单 | 池间碎片化，混合模型下容量漂移 | 实测否决：Kimi-Linear 上容量损失超过 5% |

## 测试与验证方案（必选）

*如何证明改动正确，以及 PR 会带哪些证据。*

**注：[PR 测试要求](../../developer_guide/contribution/testing.md#pr-testing-requirements) 规定了 PR 所需的证据，本节在动手实现前就规划这些证据。**

> **写作要求**：
>
> - **单元测试**：指明 `tests/ut/` 下的测试文件及其覆盖的用例，包括边界场景（空输入、单元素、最小/最大值、序列长度上限）。
> - **E2E 测试**：指明 `tests/e2e/models/configs/` 下的配置 YAML、模型、硬件（`A2` / `A3` / `A5`）以及带阈值的精度指标。
> - **性能验证**：给出基线与目标、模型、NPU 型号、卡数、部署模式、输入输出长度和并发数。不要省略指标定义。
> - **CI 可验证的部分**：说明哪些检查无需 NPU 硬件即可完成（CPU 上的 `tests/ut`、`bash format.sh ci`），让评审者知道哪些已被预验证。
> - **完成标准**：在把 RFC 标记为 `已实现` 之前必须成立的明确条件。

**示例**：

| 层次 | 覆盖内容 | 证据 |
|------|------|------|
| 单元测试 | planner 分组、page 尺寸计算、分配/驱逐顺序、空洞处理 | 随首个 PR 新增 `tests/ut/core/test_kv_cache_planner.py` |
| 单元测试（边界） | 零长度请求、大于单个 page 的请求、单 group、全部 group 已缓存 | 同一文件，以 `pytest.mark.parametrize` 标注 |
| E2E | Kimi-Linear-48B 与 DSV4.1-Flash 的精度与吞吐 | 在 `tests/e2e/models/configs/` 新增 YAML，`A2` 8 卡，GPQA 与标准精度集 |
| CI（无 NPU） | 单元测试与 lint | `TORCH_DEVICE_BACKEND_AUTOLOAD=0 pytest -sv tests/ut`、`bash format.sh ci` |

## 上线与迁移（可选）

*改动如何在不破坏用户的前提下落地：实施阶段、开关、分支计划、废弃策略。*

**注：改动较大、破坏既有行为或跨多个版本时必选。**

> **写作要求**：
>
> - 把实现拆成可独立评审与合入的阶段，并标注每个阶段对应 RFC 的哪一节。
> - 说明新增开关的默认状态，以及用户如何开启与关闭。
> - 若既有用户会遇到行为变化，给出迁移步骤以及「什么都不做」时的结果。
> - 说明分支计划：是否需要 `rfc/<feature-name>` 特性分支、哪些维护者批准、何时合回主干。
> - 说明任何临时兼容代码的移除或后续计划。

**示例**：

| 阶段 | 内容 | 默认状态 | 合入条件 |
|------|------|------|------|
| 1 | 分组可插拔，保留旧 allocator | 旧行为 | 既有一切模型分组的单测覆盖齐全 |
| 2 | large page allocator，通过 `additional_config` 选择启用 | 关闭 | 4 个已验证混合模型精度对齐 |
| 3 | large page 成为默认，移除旧路径 | 开启 | 启用状态下运行一个版本无回归 |

工作落在 `rfc/large-page-kv-cache` 分支（经两位维护者批准），每个阶段一个 PR。旧路径在阶段 3 之后的一个版本移除，release note fragment 记录默认行为的变化。

## 待决问题（可选）

*尚未定论的问题，尽量附带解决路径。*

> **写作要求**：
>
> - 每个问题单独编号，给出备选项、无人回应时的默认结论，以及应当由谁回答。
> - 不要用本节掩盖缺失的设计。若某个问题会阻塞设计，说明该 RFC 尚未就绪。
> - 问题解决后删除，并把结论记录到对应章节。

**示例**：

1. **是否允许显式 `--block-size` 小于 64 token？** 方案 A：可行时允许；方案 B：钳制到 kernel 最小值。默认取 A，除非某个 kernel 无法表达更小的 block。负责人：attention kernel 维护者。
2. **是否为兼容保留一个版本的 `hash_block_size` 别名？** 默认：保留，并给出弃用告警。
