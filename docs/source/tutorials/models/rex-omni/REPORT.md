# Rex-Omni 单卡 Ascend 910B3 部署优化报告

日期：2026-11-04 · 硬件：单卡 910B3（64 GB HBM）· 模型：Rex-Omni（Qwen2.5-VL-3B，bf16）

## 1. 结论摘要

在 Dense200 box_eval 全量 200 张上：

| 指标 | 初始可复现基线 | 纯吞吐优化 | 提前停止 | +FULL graph +32k 分块 | **推荐部署配置（+并行预处理）** |
|---|---|---|---|---|---|
| 吞吐 | 0.472 img/s | 2.111 img/s（2.113 / 2.109） | 2.441 img/s（2.449 / 2.432） | 3.197 img/s（3.205 / 3.189） | **3.651 img/s**（3.672 / 3.631） |
| 200 张总推理耗时 | 424 s | 95 s | 82 s（81.7 / 82.2） | 62.6 s（62.4 / 62.7） | **54.8 s**（54.5 / 55.1） |
| 摊销单图耗时 | 1.64 s（batch 墙钟/64） | 0.475 s | 0.410 s | 0.313 s | **0.274 s** |
| 输出吞吐 | 291 tok/s | 1079–1106 tok/s | 879–895 tok/s | 1216 / 1189 tok/s | 1341 / 1330 tok/s |
| F1@0.5 | 0.6896 | 0.7064（0.7058 / 0.7070） | 0.7481（0.7483 / 0.7478） | 0.7474（0.7474 / 0.7474） | **0.7554**（0.7539 / 0.7569） |
| mIoU-F1（IoU 0.5–0.95） | 0.5075 | 0.5157（0.5144 / 0.5169） | 0.5428（0.5431 / 0.5425） | 0.5426（0.5425 / 0.5427） | **0.5486**（0.5488 / 0.5483） |

推荐部署配置相对初始基线：**吞吐 7.74×，F1 +0.066，mIoU-F1 +0.041**（均为两次全量均值）。
相对单请求 bs=1（0.046 img/s）：约 **79×**。

**推荐部署配置分六层，逐层叠加**：

1. **调度/输入/输出参数**（`batch=200` 一次性提交 + `max_pixels=1003520` +
   `max_tokens=2048` + `max_model_len=4096` + `repetition_penalty=1.05`）→ 2.11 img/s；
2. **解析器去重**（`rex_omni/parser.py`，未 commit）：吞吐不变，F1 0.706 → 0.7237 / 0.7191；
3. **生成侧提前停止 + 关闭 async scheduling**（`rex_omni/early_stop.py` +
   `--early-stop-repeats 5 --extra '{"async_scheduling": false}'`）：吞吐再 +17%，
   F1 再 +0.005（0.7483 / 0.7478），顶满 `max_tokens` 的样本 7/7 被提前截短；
4. **FULL_DECODE_ONLY ACL graph**（`compilation_config.cudagraph_mode`）：把整段
   decode 收进一张图，吞吐再 **+27%**（64.5 s / 3.10 img/s），精度在噪声内；
5. **加大 prefill 分块**（`max_num_batched_tokens=32768`）：chunk 数 23 → 6，
   吞吐再 **+3%**（62.6 s / 3.20 img/s），F1 0.7474 两次完全一致；
6. **并行输入预处理**（wrapper 的 `REX_OMNI_VIS_WORKERS=8` +
   `run_eval.py --load-workers 8`）：读图与 `process_vision_info` 用线程池并行，
   吞吐再 **+14.2%**（54.8 s / 3.65 img/s），F1 0.7554 / 0.7569 在噪声内。

> 注 1：推荐配置的输出 tok/s 与纯吞吐优化同量级或更高（1216/1189 vs 1106），
> 因为墙钟下降；提前停止截掉的是退化 token，正常样本不受影响。
>
>
> 注 2：async scheduling 开关会显著改变生成结果（开/关两轮仅 15/200 输出完全一致）。
> 在本环境实测关闭后 F1 高约 0.02 且吞吐基本不变（2.08 vs 2.11 img/s），因此推荐关闭；
> 该精度差异的机制尚未完全定位，属于经验结论。
>
> 注 3（2026-11-05）：复核了 vLLM 引擎内的 CPU 输入预处理多线程
> （`OMP_NUM_THREADS=8`）。预处理墙钟 14 s → 7 s，但端到端 62.6 → 63.1 s
> （两轮均值，无差异），已否决，详见发现 14。
>
> 注 4（2026-11-05 续）：发现 14 中"约 5.6 s 来源不明的启动延迟"已定位——
> 不是引擎启动，而是 Rex-Omni wrapper 里逐条串行的 `process_vision_info()`。
> 它与 PIL 读图一起并行化后，端到端 62.6 → **54.8 s（+14.2%）**，见发现 15。
> 推荐部署配置据此增加第 6 层。

## 2. 关键发现

1. **并发是唯一量级级别的杠杆。** bs=1 → 64 → 200 时吞吐 0.046 → 0.472 → 1.22 img/s。
   固定分块（64/64/64/8）的块间屏障由最慢请求决定；一次性提交 200 条让 continuous
   batching 摊平长尾，同配置直接 2.58×。
2. **超长输出是退化重复，不是上下文不够。** 24–28/200 的样本会循环生成同一个框
   （单条最多重复 1572 次）。此前 26/200 的“4096 截断”截掉的正是这些垃圾 token。
   把 `max_model_len` 提到 8192 后模型继续重复到 8192，精度无提升、耗时 2.2×；
   反之 `max_tokens=2048` 截掉尾巴，精度不变而吞吐 +50%。
3. **降低输入分辨率仍然划算。** `max_pixels` 2M → 1M 使平均 prompt 1378 → 942 tok，
   全量再提速 19%（1.77 → 2.11 img/s），精度在噪声内。
4. **greedy 解码不是 batch-invariant。** 同数据 b64 与 b200 仅 16/200 输出完全一致。
   子集上 ±0.02 的 F1 差异多为噪声；8k/8k 在 40 张子集上的 +2.0pt 未在全量复现。
5. **重复惩罚不是解药。** rep=1.1 无实质改善，rep=1.2 损害召回（F1 0.674）。
6. **解析器去重是低成本的精度补丁。** 退化重复会在输出里留下完全相同的框，官方 metric 把它们
   计为额外 FP。按类别丢弃完全重复的坐标元组后，26/200 的受影响样本被清理，
   F1 +0.013～0.018（0.7237 / 0.7191 vs 0.7058 / 0.7070），吞吐不变。
   注意这是**解析后处理**，重复 token 仍然被生成，不节省算力。
7. **生成侧提前停止真正省算力。** 自定义 vLLM logits processor 监测输出 token 的精确周期：
   尾部出现 5 次完全相同的 token 块即强制 EOS。关闭 async scheduling 后两次全量：
   输出 token 均值 390 → 349（−11%），耗时 97.2 / 95.3 s → 81.7 / 82.2 s（**−14～16%**），
   吞吐 2.058 / 2.098 → **2.449 / 2.432 img/s**；7 条顶满 2048 的退化样本全部被截短，
   正常样本无截断，F1 0.7426 / 0.7447 → 0.7483 / 0.7478（噪声内）。
8. **async scheduling 在本 vllm-ascend 版本会隐藏生成历史。** 其 `_sample` 覆写漏调
   `update_async_output_token_ids()`，logits processor 看到的是 `-1` 占位符，
   因此依赖历史 token 的处理器必须关闭 async scheduling。开关同时改变生成结果
   （仅 15/200 完全一致），关闭后 F1 约 +0.02，机制未完全定位。
9. **耗时结构（2026-11-05 二次校正）**：早期把 `max_tokens=1` 探针的 26.6 s 整体当作
   prefill，口径有误——该探针还包含图像加载和 wrapper 的串行 `process_vision_info()`。
   用同一探针叠加 0.3 s 间隔的 `npu-smi` 采样，并用 `startup_trace.py` 给每条请求的
   预处理打时间戳后，最终配置 **54.8 s** 的构成是：
   **图像加载 0.5 s（1%）+ `process_vision_info` 1.0 s（2%）+ 引擎启动约 0.3 s（<1%）+
   prefill 17.4 s（32%）+ decode 36.0 s（66%）**（后两项按对照推算，与并行化无关）。
   并行化前的对应数字是 3.6 + 7.3 + 约 0.3 s；原先估计的"5.6 s 引擎启动"并不存在，
   那段时间就是串行预处理。decode 仍是绝对大头，且集中在长尾低并发段。
   输出 token 已接近格式下限（约 5.0–5.2 tok/框，300 框样本约 1560 tok），
   靠压缩输出长度的空间很小，下一步是减少 decode 步数。
10. **分辨率 1M 已是边界。** 全量把 `max_pixels` 再降到 802,816（prompt 942 → 832 tok）
   反而更慢更差：86.9 s / 2.30 img/s / F1 0.7339 / mIoU-F1 0.5269（1M 为 82 s /
   2.44 / 0.7481 / 0.5428）。降分辨率改变了生成结果（输出 tok 345 → 358），
   抵消了 prefill 收益并损害精度，不建议再降。
11. **NPU profiling 定位：长尾是算子下发，不是 KV 带宽或算力。**
   全程采样 AICore 41%、HBM 带宽 18%（decode 阶段 45% / 22%）——注意 41% 是**含约
   9–10 s 空转**的均值（见发现 14），逐秒时间线显示生成段 AICore 中位数 38%、
   **p90 打到 100%**，准确说法是"低并发长尾不受限，满载段会吃满算力"；单步延迟
   bs=1 27.8 ms、bs=8 30.2 ms、bs=32 35.8 ms、bs=200 85.0 ms，bs≤8 几乎不变，
   存在约 28 ms 的固定 per-step 开销。`torch_npu.profiler` 显示 bs=1 时每步
   kernel 仅 9.5 ms、空档 22.8 ms，host ACL API 约 14 ms/步（~196 次 launch/步，
   36 次 attention + 36 次 cache-update + 42 次 copy + 77 次 fill）。
   async scheduling 开关对单步延迟无影响（25.9 vs 25.0 ms @bs=1）。
   FULL graph 之前，全量 82 s 中长尾（301 框样本约 1560 步）以低并发跑约 1300 步，
   约 36 s 就是这笔固定开销。**结论：W8A8 与继续调参收益有限，剩余空间在
   vllm-ascend 的 graph 覆盖/算子融合，或减少 decode 步数（投机解码）。**
   （该结论直接催生了发现 12，已兑现 17 s。）
12. **FULL_DECODE_ONLY ACL graph 把整段 decode 收进一张图，吃掉下发开销。**
   默认 `PIECEWISE` 只归并部分子图，attention / ReshapeAndCache 等仍逐算子下发。
   改用 `compilation_config={"cudagraph_mode": "FULL_DECODE_ONLY",
   "cudagraph_capture_sizes": [...]}` 后，单步延迟 bs=1 27.8 → **10.4 ms**、
   bs=8 30.2 → **12.3 ms**、bs=32 35.8 → **17.1 ms**（低并发 2.1–2.7×）；
   全量 200 张两次：82 → **64.5 s**（65.0 / 63.9），吞吐 2.44 → **3.10 img/s
   （+27%，3.078 / 3.128）**，F1 0.7481 → 0.7474（0.7457 / 0.7490）、
   mIoU-F1 0.5428 → 0.5428（0.5418 / 0.5437），均在 run-to-run 噪声内。
   图捕获仅增加 3 s、0.26 GiB；捕获尺寸列表必须覆盖线上 batch 分桶
   （本配置 `[1,8,16,32,64,128,200,256]`）。官方提示捕获过多尺寸可能 OOM/挂起，
   如遇问题降低 `gpu_memory_utilization` 或减少尺寸。
   注意：graph 内算子融合带来细微数值差异，greedy 输出 183/200 与 PIECEWISE 不同，
   但平均输出长度几乎一致（348.85 vs 349.1 token），无退化。
13. **prefill 分块加大到 32k 再省约 2 s。** `max_num_batched_tokens` 默认 8192，
   200 条共约 18.8 万 prompt token 要切 23 个 chunk；提到 32768 后只需约 6 个，
   全量 64.5 → **62.6 s（62.4 / 62.7）**，3.10 → **3.20 img/s（+3%）**，
   F1/mIoU 不变（0.7474 / 0.5426，两次一致）。load 时间 +2 s，未见 OOM。
   再往 65536 的收益预计 <1%，未测。

14. **CPU 图像预处理多线程（`OMP_NUM_THREADS=8`）：实测无收益，已否决（2026-11-05）。**
   `npu-smi` 逐 0.3 s 时间线显示每次运行中段有约 9–10 s AICore 全为 0；vLLM 在
   `OMP_NUM_THREADS` 未设置时把输入预处理压到单线程（`multiproc_executor.py:887`、
   `input_processor.py:502`）。离线测 200 张预处理 1 线程 25.3 s → 8 线程 8.5 s（3.0×），
   当时预计全量可提速 13–16%。实测（推荐配置不变，只改线程数）：

   | 运行 | 总耗时 | img/s | 输出 tok/s | F1@0.5 |
   |---|---|---|---|---|
   | 同场对照（t=1） | 62.57 s | 3.196 | 1235 | 0.7554 |
   | OMP=8 第 1 轮 | 61.03 s | 3.277 | 1240 | 0.7460 |
   | OMP=8 第 2 轮 | 65.16 s | 3.069 | 1164 | 0.7493 |

   两轮均值 63.1 s，比同场对照还慢 0.8%，差异被 ±3% 的 run-to-run 波动覆盖，精度不变。
   **决定性证据**：`max_tokens=1` 隔离探针中，200 条预处理墙钟 14 s → 7 s 的同时，
   端到端只从 26.62 s 降到 26.15 s（−0.5 s）——预处理与引擎执行重叠，不在关键路径上
   （vLLM V1 的 EngineCore 是常驻进程、请求流式送入）。**结论：不设 `OMP_NUM_THREADS`，
   保持默认。** 教训：CPU 侧"看起来很忙"不等于在关键路径，先用隔离探针量一次。

15. **并行输入预处理：+14.2%（2026-11-05，本轮第二收益）。**
   `startup_trace.py`（单进程引擎 + monkey-patch `InputProcessor.process_inputs` /
   `LLMEngine.step`）显示，200 条请求的预处理是逐条串行完成的，最后一条开始时引擎
   已经空等数秒。两段都发生在请求入队之前，因此**确实**在关键路径上：

   | 阶段 | 串行（200 张） | 8 线程 | 加速 |
   |---|---|---|---|
   | `run_eval.py` PIL open + convert | 3.59 s | **0.54 s** | 6.6× |
   | wrapper `process_vision_info`（resize 等） | 7.28 s | **1.04 s** | 7.0× |
   | 合计 | 10.87 s | **1.58 s** | −9.3 s |

   微基准见 `profiling/vispar_microbench.py`；串行与并行的图像张量逐字节一致，
   全量 200 条 `num_prompt_tokens` 与对照完全相同（平均 942.0）。全量实测：

   | 运行 | 总耗时 | img/s | F1@0.5 | mIoU-F1 |
   |---|---|---|---|---|
   | 同场对照（串行） | 62.57 s | 3.196 | 0.7554 | 0.5493 |
   | 仅 wrapper 并行 | 58.00 s | 3.448 | 0.7428 | 0.5376 |
   | **两段都并行 #1** | **54.46 s** | **3.672** | 0.7539 | 0.5488 |
   | **两段都并行 #2** | **55.09 s** | **3.631** | 0.7569 | 0.5483 |

   均值 **54.8 s / 3.65 img/s（+14.2%）**，NPU 首段空转 9.8 → 0.9 / 1.9 s。
   精度差 ≤0.013，在噪声带内。这是 pure client-side 优化，未改推理栈；图片数很少
   或线程数超过容器 CPU 配额时收益缩小。与发现 14 的对照说明：**判据不是"CPU 还是
   NPU"，而是这段工作有没有被别的执行流掩盖。**

> 后者是长尾样本（301 框）更早触发提前停止、输出更短所致，速度快 18% 但 F1 低约 0.01。

> 启用 FULL graph 后两次为 65.0 / 63.9 s，波动收窄到 1.7%，说明固定下发开销被
> 消掉后，墙钟对早停触发时机的敏感度也下降。

### 3.1 请求级延迟（2026-11-05 复测，`disable_log_stats=false`）

| 口径 | 基线 | 优化后 | 变化 |

## 5. 后续工作

FULL graph + 32k prefill 分块 + 并行输入预处理已兑现 profiling 指出的三块大头
（82 → 62.6 → 54.8 s）。后续按剩余占比排序：

1. **decode 仍是绝对大头（66%）**：二次校正后的时间结构为 图像加载 0.5 s（1%）+
   `process_vision_info` 1.0 s（2%）+ 引擎启动约 0.3 s（<1%）+ prefill 17.4 s（32%）+
   decode 36.0 s（66%），见发现 9。prefill 段 AICore 已接近打满，图覆盖/继续加大
   分块收益有限（8192 → 32768 已给 +3%，65536 预计 <1%）。
2. **减少 decode 步数**：36.0 s 的 decode 中长尾仍占一半以上，这是唯一还能拿到
   两位数百分比收益的方向。投机解码最直接（长尾步数减半即墙钟减半），但本模型
   无现成 draft/MTP，需要自训；与 FULL graph 的兼容性需验证（graph 捕获单步 forward）。
3. ~~**图像加载并行化**~~ **已完成（发现 15）**：读图 + `process_vision_info`
   并行化，CPU 段 10.9 → 1.6 s，端到端 +14.2%。剩余 CPU 侧空间很小，
   下一步只能减少图像像素量本身（会伤精度）。
4. ~~**定位 5.6 s 启动延迟**~~ **已证伪（发现 15）**：那段时间不是引擎启动，而是
   wrapper 里串行的 `process_vision_info()`，已修复；真正的引擎启动仅约 0.3 s。
5. **图覆盖 / 算子融合：剩余空间约 5–10%，优先级低于上面几项。**
   算子级统计（bs=1 decode，设备时间）MatMulV2 67.7%、FusedInferAttention 10.7%、
   Rope 6.3%、RMSNorm 2.5%、SwiGLU 2.3%、Scatter/Fill/Slice/Cast 5.4%——
   可融合的部分上限约 11%，现实收益打对折约 5%；`CUDAGraphMode.FULL`（含 prefill）
   在 vllm-ascend 可配，但只有约 6 个 32k chunk，预期 ≤1–2 s。
6. **线上 continuous serving**：长尾天然被新请求填满，离线封闭批的 54.8 s 不代表线上吞吐；
   建议用 AsyncLLMEngine 持续投喂，并以稳态吞吐而非单批墙钟做容量规划。
7. **FULL graph 的稳定性回归**：vllm-ascend 标记为 experimental；升级版本、换数据集、
   改 batch 分桶后都要重测。捕获尺寸越多内存越大（本次 8 个尺寸仅 0.26 GiB，
   但官方提示可能 OOM/挂起）；如遇异常先降 `gpu_memory_utilization` 或减少尺寸。
   graph 内融合会带来细微数值差异（greedy 183/200 与 PIECEWISE 不同），
   对精度敏感的场景需做输出级回归。
