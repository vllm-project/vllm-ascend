# 接口映射生成器代码演进说明

本文说明 `generate_interface_boundaries.py` 为什么从早期脚本增长到一万多行，以及每一轮修改解决了什么问题。

这里所说的“接口映射”是指：从 vllm-ascend 源码中识别它对 vLLM 上游的 patch、继承和已验证 override 关系，再把这些关系保存成可供 CI 校验的边界数据。

## 一、先说结论

代码变大，主要不是因为接口数量从几百个增加到了几千个，而是因为脚本从“查找几种简单 AST 写法”逐步变成了一个针对 Python 源码的静态分析器。

它现在需要回答的不只是“代码里有没有 `A.f = B.f`”，还要回答下面这些问题：

- 这段代码在 vLLM main 分支上是否真的会执行；
- patch 的对象经过变量、函数参数和多层 helper 传递后，最终是谁；
- `try/except/finally`、`if`、`return`、`break` 等控制流之后，哪个定义才是运行时最终定义；
- 继承链是否完整，真正被 override 的父类方法是哪一个；
- `property`、`classmethod`、`staticmethod` 和普通方法的调用方式是否一致；
- 装饰器或 wrapper 改写签名后，调用方实际能传哪些参数；
- 分析不出来时，是上游真的缺接口，还是脚本能力不足；
- 每一个结论能否给出文件、行号、分支条件和来源 commit，方便人工复查。

因此，代码增长的本质是“分析精度和可解释性增加”，不是简单地把每个接口手写成一段 UT。

但也需要承认：`generate_interface_boundaries.py` 单文件达到一万行，已经是明显的可维护性问题。功能复杂度有客观原因，文件组织仍然需要重构。

## 二、现在到底有多少代码

以下统计以编写本文前最后一个功能实现 commit `992b32ac0` 为准，不包含本文自身：

| 文件 | 行数 | 作用 |
|---|---:|---|
| `generate_interface_boundaries.py` | 10,270 | 主生成器：解析源码并生成依赖关系表 |
| `audit_interface_boundary_coverage.py` | 1,911 | 独立审计器：从另一个入口检查主生成器有没有漏掉候选点 |
| `test_generate_interface_boundaries.py` | 10,010 | 主生成器回归测试 |
| `test_audit_interface_boundary_coverage.py` | 1,167 | 独立审计器回归测试 |
| `GENERATOR_CHANGELOG.md` | 1,312 | 英文技术变更记录 |
| `README.md` | 88 | 使用说明 |
| **合计** | **24,758** | 生成器、审计器、测试和文档的总量 |

所以“现在有两万多行”并不等于主脚本有两万多行：

- 主生成器约占 41.5%；
- 两个测试文件约占 45.1%；
- 独立审计器约占 7.7%；
- 文档约占 5.7%。

测试代码与主生成器规模接近，是因为每修复一种复杂写法，都需要同时增加：

1. 一个能复现遗漏或误报的失败用例；
2. 一个相似但不应被识别的对照用例；
3. 对输出状态、原因、证据和签名的断言；
4. 防止以后修改时同一问题再次出现的回归用例。

## 六、为什么还要单独写 1911 行审计器

主生成器如果自己检查自己，很容易出现同一个盲区：生成器没识别某种写法，它的自检也可能看不到这种写法。

因此增加了 `audit_interface_boundary_coverage.py`。它用更简单、相对独立的规则重新扫描下游候选点，然后检查每个候选点在主结果中是否恰好有一种去向：已验证、风险、预期注入、排除或待复查。

审计器不是第二份完整生成器，也不能复用主生成器的所有复杂推导，否则会失去独立检查的意义。

它的主要演进如下：

| 版本 | 修改内容 | 解决的问题 |
|---|---|---|
| coverage audit v0.1 | 建立第二个 AST 候选扫描器 | 检查主生成器有没有整类遗漏候选点 |
| coverage audit v0.3 | 加入精确外部源码、严格 C3 MRO 和 SHA 校验 | 审计器与生成器使用同一份可复现源码基础，但保留独立枚举逻辑；当时达到 1018/1018 候选点有明确去向 |
| coverage audit v0.4 | 识别缺失 `super()` 的风险并要求所有候选分类 | 防止父方法不存在的 override 被漏掉；覆盖 1019/1019 |
| coverage audit v0.5 | 增加 descriptor 补充扫描规则 | 独立发现 property/classmethod 等候选 |
| coverage audit v0.6 | 支持 helper 实参和字面量 `sys.modules` | 覆盖间接 helper patch 候选 |
| coverage audit v0.7 | 支持 MRO 选模块 helper；禁止进入上游或外部 helper 函数体重新解释普通赋值 | 修复把上游正常字段赋值误当下游 patch 的假阳性；最终覆盖 1023/1023 |

独立审计器从 978 行增长到 1911 行；对应测试从 269 行增长到 1167 行。这部分是有意保留的“不同视角”，不是简单重复拷贝。

## 七、为什么测试代码也有一万多行

当前主生成器测试从最初的 771 行增长到 10010 行。测试量大的原因包括：

- Python 静态分析的边界组合很多，例如同一语法放在函数、类、条件、异常或 helper 中，含义会不同；
- 每种新规则都需要正例和反例，否则修复漏报时很容易引入误报；
- 被否决的 v0.18、v0.20、v0.21 都说明，只验证“新场景通过”不够，还要验证原有场景没有倒退；
- 结果不只有关系本身，还包括状态、原因码、签名、证据行号、分支和来源 SHA，这些都需要测试；
- 继承和签名判断必须坚持“不完整就不猜”，因此还要为每种不完整条件写 fail-closed 测试。

换句话说，测试行数大不是生产代码量失控的直接原因，而是当前精度主要依靠大量回归样例守住。

## 八、哪些增长是必要能力，哪些属于技术债

### 有必要保留的能力

- 完整 C3 MRO 和“不完整不猜”；
- main/NPU 分支可达性；
- helper 参数和 owner 传播；
- 最终运行时绑定，而不是随便选择第一个定义；
- descriptor 和调用签名兼容；
- 无法证明时明确标为 review，而不是静默丢弃；
- 来源 SHA、文件、行号和判断原因；
- 与主生成器相对独立的覆盖审计器；
- 每个历史 bug 的回归测试。

这些能力直接服务于“自动生成的依赖关系表要准确、完整，并且不能靠猜”的目标。删除后代码会变短，但会重新出现已经解决的漏报或误报。

### 当前明显的技术债

- 10270 行集中在一个主文件中，阅读和修改成本很高；
- 作用域、控制流、patch、MRO、签名和序列化逻辑耦合在同一个类中；
- v0.17～v0.24 为处理复杂控制流持续扩展状态模型，局部逻辑较难理解；
- 一些规则是针对固定上游 SHA 或固定第三方实现的精确适配，需要清晰隔离；
- 测试文件同样达到一万行，按能力查找场景不方便；
- 文档虽然记录了版本，但“功能代码在哪一层”不够直观。

## 九、建议怎么重构

不建议为了把行数降下来直接重写算法。当前能力是通过多轮真实反例积累出来的，大规模重写很容易让旧问题重新出现。

更稳妥的方式是先做不改变行为的机械拆分：

| 建议模块 | 放入的能力 |
|---|---|
| `models.py` | 关系、finding、签名、descriptor、证据等数据模型 |
| `source_index.py` | Python 文件、module、class、method 和外部源码索引 |
| `scope_flow.py` | 词法作用域、条件、异常、循环和路径状态 |
| `patch_flow.py` | patch owner、helper 传播、`setattr`、`sys.modules` 等规则 |
| `mro.py` | C3 MRO、父类解析、override 和继承完整性 |
| `signature_contract.py` | descriptor、wrapper、decorator、Triton 和签名兼容 |
| `schema.py` | JSONL schema、序列化、读取和对比报告 |
| `generate_interface_boundaries.py` | 只保留参数解析和各模块编排 |

测试也可以按相同能力拆成多个文件。这样主入口有机会缩到约 500～1000 行，但总代码量不会显著减少，因为复杂能力仍然存在。

重构时应满足三个条件：

1. 现有测试全部保持通过；
2. 同一份上下游源码生成的 JSONL 完全一致；
3. 独立审计器仍然保持所有候选点都有且只有一个分类。

## 十、如何理解“每次修改”的提交方式

后期修改通常拆成三类 commit：

1. **红灯测试 commit**：先加入能够复现问题的测试，证明旧代码确实失败；
2. **实现 commit**：修改分析器，使新场景通过，同时保证旧场景不回归；
3. **记录或基线 commit**：更新 changelog、生成结果或审计基线。

所以 Git 中的 commit 数会多于 v0.3～v0.36 的版本数。本文按“一个完整能力修改”汇总，而不是把测试、实现和文档三个 commit 重复写成三项。

需要查看更细的英文提交级记录，可以阅读同目录下的 `GENERATOR_CHANGELOG.md`。本文是它的中文解释版，并补充了代码规模、增长原因和重构建议。

## 十二、最终判断

这次从 2320 行增长到 10270 行，大部分增长能够对应到一个明确的漏报、误报或可复现性问题，其中 v0.13～v0.23 的间接 patch 和控制流分析占比最大。

因此，不能简单得出“代码多是因为写坏了”或者“删回一千行也能保持同样准确度”的结论。但同样不能认为当前结构已经合理：功能复杂度基本有依据，单文件组织方式需要尽快治理。

后续最合理的目标不是只看行数，而是：

- 不降低依赖关系表的准确度和覆盖率；
- 保持“分析不完整就不猜”；
- 先拆模块、拆测试，再评估能否合并重复状态和公共逻辑；
- 每次功能修改继续记录“问题样例、误报/漏报原因、代码改动和回归测试”。
