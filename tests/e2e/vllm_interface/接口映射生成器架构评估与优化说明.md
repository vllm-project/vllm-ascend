# 接口映射生成器架构评估与优化说明

本文评估 `generate_interface_boundaries.py` 在 v0.3～v0.36 演进过程中的合理性、冗余和架构问题，并记录本轮已经完成的行为不变重构。

## 一、总体判断

功能演进总体合理，架构演进明显滞后。

脚本变大主要是因为真实源码中存在复杂 patch、helper 传递、条件和异常路径、多继承、descriptor、decorator 和运行时签名，并不是简单复制粘贴出了一万行代码。

但是，从 v0.13 开始，新的控制流和 patch 能力持续追加到同一个类；从 v0.24 开始，descriptor 和签名分析也继续进入这个类。最终形成了一个同时负责源码索引、MRO、patch、签名、finding 和报告的超大模块。

因此需要同时接受两个结论：

1. 不能为了减少行数删除已有静态分析能力，否则会重新出现已修复的漏报和误报；
2. 当前单文件和超大类的组织方式确实需要分阶段重构。

## 二、发现了哪些确切问题

### 1. 主类职责过多

重构前，`InterfaceBoundaryGenerator` 有约 5629 行、115 个方法，同时负责：

- 上下游 repository 路由；
- MRO、inheritance 和 override；
- patch owner、helper 参数和控制流传播；
- descriptor、decorator 和签名 contract；
- relation/finding 构造、去重和排序；
- JSONL 编码和基线对比。

这是典型的 God Class。修改一个能力时，需要理解大量与当前问题无关的状态。

### 2. `RepositoryIndex._parse()` 单方法过大

该方法约 646 行，同时处理：

- 文件读取和 AST 解析；
- import、class、function 和 value 建模；
- property 和 descriptor；
- alias、final binding 和 lazy export；
- 多张全局索引更新。

这会增加索引状态不一致的风险，也让性能分析和单元测试难以聚焦。

### 3. 存在多套相似但语义不同的控制流分析

当前有多套 walker 分别处理：

- 普通作用域最终绑定；
- main 分支语句选择；
- private helper 调用传播；
- patch 语句传播；
- 独立 auditor 候选扫描。

它们都处理 `if`、`try`、循环、`return`、`raise` 等语法，但状态模型和输出目的不同。

这里确实存在重复框架，但不能简单合并。尤其独立 auditor 必须与生成器保持相对独立，否则会变成“生成器自己证明自己没有遗漏”。

### 4. `PatchScanContext` 多张状态表可能不同步

它同时维护：

- `bindings`；
- `binding_alternatives`；
- `unknown_bindings`；
- `upstream_binding_provenance`；
- `upstream_binding_history`；
- 字符串、local callable 和 runtime module 等状态。

旧代码虽然已有 `bind_exact()` 等方法，但多个位置仍直接同时修改两张或多张字典。后续开发者如果漏改一张表，就可能产生静默错误。

### 5. 多张索引保存“代表值”和“全部变体”

例如：

- `callables` 和 `callable_variants`；
- `classes` 和 `class_variants`；
- `methods` 和 `method_variants`；
- `descriptor_kind` 和 `descriptor_variants`。

这些数据不是简单重复：代表值用于快速查询，variants 用于条件定义和最终绑定。但以前缺少统一一致性检查，存在一张表更新、另一张表未更新的风险。

### 6. 存在少量真实死代码和未消费字段

本轮确认并删除了：

- 生成器中 5 个从未调用的私有方法；
- auditor 中 1 个从未调用的方法；
- 已经收集但从未读取的 `string_constants` 数据链；
- 只写不读的 property accessor 全局缓存；
- 只保存但不使用的 helper identity 字段；
- 只保存但不读取的 `ModuleInfo.typed_lazy_exports` 字段。

死代码存在，但不是脚本从 2320 行增长到一万行的主要原因。

### 7. 签名仍使用六槽 list

内部签名形式大致为：

```text
[同步类型, 位置专用参数, 普通参数, *args, 关键字专用参数, **kwargs]
```

大量代码通过 `[0]`～`[5]` 读取内容，可读性较差。长期应该使用 `SignatureShape` 数据类，只在 JSON 边界转成旧 list。

本轮没有修改这一部分，因为它会影响所有签名比较，是准确性风险较高的架构重写。

### 8. 存在性能结构问题

`RepositoryIndex` 会针对不同函数和装饰器重复从作用域开头计算状态，真实固定源码的一次完整生成耗时 782.4 秒。

长期可以建立每个 module/class 的前缀状态表，把重复计算改为查询。但状态必须不可变或在返回时 clone，否则不同调用点会串状态。本轮没有加入缓存，避免引入静默漏识别。

### 9. property accessor contract 目前只在内存中计算

`Relation` 中已经保存 upstream/downstream/installed property accessor 信息，但 schema v6 没有把它写入 JSON，也没有在 `compare_relations()` 中比较。

这不是可以直接删除的普通冗余，而是一个需要单独决策的能力缺口：

- 如果 accessor 是需要看护的接口，应在 schema v7 中持久化和比较；
- 如果只看 descriptor kind，应明确说明后再删除整条 accessor 数据链。

本轮选择保留，避免误删潜在接口能力。

## 三、本轮完成了哪些优化

### 提交一：收口状态更新并清理死代码

Commit：`17e60d5a8`

主要修改：

- 为 `PatchScanContext` 增加统一的 resolution 更新、清理和 lexical shadow 方法；
- 替换散落的多字典直接写入；
- 增加 representative/variants 索引一致性检查，不一致时 fail closed；
- 删除确认无调用、无消费的代码和字段；
- 增加 3 个状态与索引回归测试。

解决的问题：

- 降低 bindings 和 alternatives 不同步的风险；
- 防止代表 callable 与第一个 variant 静默漂移；
- 清除历史版本遗留但已经没有作用的代码。

### 提交二：拆分 schema 和报告职责

Commit：`e115b2409`

新增 `_interface_boundary_schema.py`，专门负责：

- relation/finding 的 schema v6 编码；
- 确定性 JSONL 写入；
- generated 与 baseline 的关系对比；
- descriptor 和 signature contract 变化报告。

原 `generate_interface_boundaries.py` 保留同名兼容入口，因此现有调用方和测试不需要修改调用方式。

同时完成两项小优化：

- descriptor 和 signature 对比复用同一组 alias 匹配结果，不再对 generated relations 重复扫描两遍；
- finding 和 relation 的下游 callable 查找合并为一个方法。

新增“多个 patch alias 冲突时仍保持旧版 first-match 语义”的回归测试，避免性能整理改变结果选择顺序。

## 四、代码规模变化应该怎么理解

| 项目 | 重构前 | 重构后 |
|---|---:|---:|
| 主生成器 | 10270 行 | 9917 行 |
| schema/report 模块 | 0 行 | 396 行 |
| 独立 auditor | 1911 行 | 1908 行 |
| 主生成器测试 | 10010 行 | 10104 行 |

主文件减少了 353 行，并第一次拆出了明确模块边界。生产代码总行数没有下降，反而因为模块说明、类型边界、兼容 facade 和新增防线略有增加。

这说明本轮优化目标不是“用更少代码实现不同语义”，而是：

- 删除确认无用的部分；
- 让状态更新集中；
- 让分析逻辑与结果编码解耦；
- 为后续继续拆分建立安全边界。

如果只追求总行数下降，可以省略类型、说明和兼容入口，但会降低可维护性，也可能破坏已有调用方式。

## 六、为什么没有一次性把一万行全部拆开

一次性拆分 patch、MRO、签名和多套控制流，会产生非常大的 diff。即使最终测试通过，也很难定位一条关系变化来自哪一步。

本轮采用的顺序是：

1. 先收口状态更新；
2. 再删除确认死代码；
3. 先拆无分析语义的 schema/report；
4. 用固定源码证明逐字节一致；
5. 后续再逐模块拆分，每一步单独做 golden 校验。

这比一次性重写更慢，但更符合“脚本自动生成结果必须完全准确”的目标。

## 七、下一步建议

建议按下面顺序继续，不要并行大改：

1. 把固定源码 golden 校验做成正式 `--check` 命令，而不是只生成 report；
2. 拆 `boundary_models.py`，保留原模块 re-export；
3. 把 `RepositoryIndex._parse()` 拆成 parse module、register module 和 materialize 三层；
4. 拆 `HierarchyResolver`，集中 MRO、inheritance 和 override；
5. 拆 `SignatureContractAnalyzer`，再引入内部 `SignatureShape`；
6. 最后才拆 `PatchAnalyzer` 和共享控制流骨架；
7. 在逐字节 golden 保护下，再优化作用域状态重复计算。

每一步必须继续满足：213 个分析器测试、1918 个边界 UT、固定源码 JSONL 语义一致和独立 auditor 1023/1023。
