# A5 INT8 / MXFP8 分块流水方案与性能记录

整理日期：2026-11-12。

## 2. 分块流水方案

### 2.1 共同调度原则

沿 token/行维度分成 K 块，默认测试 K=2、4。计算使用调用方当前流，通信使用 ProcessGroupHCCL 内部流；保留同一个通信组，不额外创建通信域或用户流。所有 rank 以相同顺序提交集合通信。

预取深度固定为 2。先提交第 0、1 块的量化与异步通信，再等待第 0 块并消费结果，随后提交下一块。这样允许后续块的量化、前面块的反量化与通信重叠。相同通信组中的通信仍保持顺序；代码允许重叠不等于设备 kernel 已经实际重叠。

`Work.wait()` 在消费数据前建立依赖。主计时结束前，所有通信都已 join 到当前流；逐块不做设备级 `synchronize()`，也不读取设备 `.item()`。测试同步、精度参考和 profiler 额外运行位于各自独立阶段。

### 2.2 MXFP8：AllToAll + BF16 AllGather

本文的 MXFP8 路线是普通集合通信组合实现：

```text
BF16 输入
→ 本地 MXFP8 E4M3FN 量化，每 32 个 hidden 元素共用 E8M0 scale
→ 原始 FP8 / scale 字节按行打包
→ AllToAll
→ owner 收到各 rank 的行分片，BF16 反量化与本地 SUM
→ BF16 AllGather，恢复完整输出
```

量化不需要先同步跨 rank 的 amax。每个 rank 的 MX scale 可以不同，必须将 FP8 值与其原始 scale 编码一起传输；不能对 scale 做数值 cast 来替代字节打包。当前布局要求 hidden 为 64 的整数倍，各块行数是 TP 的整数倍，尾部按 TP 行单位分配。

K=4 的主机提交顺序：

```text
Q0 A0 → Q1 A1 → wait(A0) D0 G0 → Q2 A2
              → wait(A1) D1 G1 → Q3 A3
              → wait(A2) D2 G2 → wait(A3) D3 G3 → wait(all G)
```

Q 是量化/打包，A 是 AllToAll，D 是 BF16 反量化/本地 SUM，G 是 BF16 AllGather。通信提交顺序为 A0、A1、G0、A2、G1、A3、G2、G3。整块有 1 次 AllToAll 和 1 次 AllGather；K 块各有 K 次，增加启动与调度开销。

反量化存储、本地 SUM 输出、AllGather 和最终输出均为 BF16；算子内部累加精度与 workspace 由后端决定。精度参考使用 FP32 不表示候选路径反量化存储为 FP32。

发送/接收队列最多持有两块。各块 AllGather 的 partial、输出视图和 Work 保留到最终 join，partial 总量约为原 BF16 张量的 1/TP。显存峰值取决于在途张量、流依赖及 allocator 回收，不会仅因已完成调用的次数而成倍累加；模型并发在途调用需单独评估。

### 2.3 INT8：整张量共享 scale + 分块 AllReduce

首版保留原有量化规则，只改变后半段调度：

```text
整张量逐通道 amax → FP32 MAX AllReduce → 共享 scale
→ Q0 / AR0(async) → Q1 / AR1(async)
→ wait(AR0) / D0 → Q2 / AR2(async)
→ wait(AR1) / D1 → … → wait(最后一个 AR) / D最后一块
```

Q 是 INT8 量化，AR 是 INT8 SUM AllReduce，D 是 BF16 反量化和写回。每次调用仍扫描完整输入，并同步一次逐通道 amax；所有块复用这一份 scale，不在块间重新计算。前置 amax/MAX 是依赖，不能通过本轮后半段流水消除。

对通道 c，尺度为：

```text
max_q = floor(127 / TP)
scale[c] = max(max_{rank, token} abs(x[rank, token, c]) / max_q, 1e-8)
q = round(x / scale)
```

TP2/4/8 对应 max_q 为 63/31/15，保证任意部分和与最终 SUM 位于 INT8 范围内。流水不增加量化等级，也不会消除 TP8 的 max_q=15 限制。

K 块有 1 次 FP32 MAX 和 K 次 INT8 SUM，无需 AllGather，也不要求块行数被 TP 整除。原始整块和分块量化应产生相同字节，通过 INT32 SUM 参考精确检查整数通信，再检查 BF16 完整输出。

“每块独立 scale”会改变量化粒度，不属于当前首版。该变体可能改变精度，必须另立实验；可将各块 amax 拼成 [K,H] 后合并做一次 MAX，而不是默认添加 K 次小 MAX 通信。

### 3.3 计时、显存和收益定义

- 主延迟使用 NPU event，排除输入复位，对每个 sample 先取最慢 rank，再汇总 p50/p95。MXFP8 包含最终 AllGather join；INT8 包含前置 amax/MAX、所有 SUM join 和 BF16 写回。
- 方案执行顺序按轮轮换；JSON 保留原始样本和各轮中位数，本次会话只提供了汇总表。
- `wall/reset` 是包含复位和主机提交的每轮批次平均时间，经跨 rank 与轮次汇总。它与 event 样本的 p50 口径不同，不能直接相减来定位 CPU 开销或被隐藏的通信。
- `extra peak MiB` 只统计测量区间内 PyTorch allocator 相对起点的额外峰值，不包括 reserved 或 HCCL 外部分配；单次峰值不是多次调用的累计量。
- benchmark 原地写回以便复用输入；MXFP8 运行时遵循通信接口约定，分配独立输出。下表显存不能直接替代 vLLM 整机峰值或模型并发时的峰值。
- profiler 在性能采样完成后另行运行；含 profiler 标签和额外同步的 trace 时长不替代下列非 profiler 测量。

```text
加速比 = 基线 p50 / 候选 p50
耗时下降百分比 = (1 - 候选 p50 / 基线 p50) × 100%
```

表中的 `vs BF16`、`vs full`、`vs chunk serial` 分别以 BF16、整块 MXFP8、相同 K 的串行为基线；大于 1 表示更快。`1.186x` 不等于耗时降低 18.6%，对应下降约 15.7%。

特别地，TP8 的 0.9672 ms（BF16）和 0.9113 ms（两块流水）对应 1.061x、耗时下降 5.78%；0.9223 ms（整块 MXFP8）和 0.9113 ms 对应 1.012x、耗时下降 1.19%。原始表保留日志已舍入的加速比，分析百分比由 p50 重新计算。

相对 L2 为 `||候选输出 - 原始输入的 FP32 SUM||₂ / max(||FP32 SUM||₂, 1e-12)`，是全张量二范数误差比例，既不是最大单元素误差，也不是平均绝对误差。`0.0293` 约为 2.93%。最大绝对误差单独统计 `max(abs(候选输出 - FP32 SUM))`。

结果支持本批分块/流水未增加可见误差，不能仅据合成输入指标认定真实模型精度已验收。

### 6.1 [16384,5120] 的核心对照

TP2/TP4 两块流水在该 shape 上，相对整块的 p50 分别降低 15.69% / 16.03%；TP8 降低 1.19%。各路线与 BF16 的比较仍应单独报告。

### 6.2 TP2：两块在三个采样点均有 p50 收益，尾延迟待观察

两块流水在三个 shape 上均超过整块，相对整块 p50 降低 14.63%、15.69%、8.36%，额外峰值显存降低约 18%～19%。

8192 tokens 的四块流水比整块慢 20.13%，表明增加块数不一定抵消启动/调度开销。32768 tokens 的四块 p50 比两块仅低约 1.06%，尚不足以仅据单批汇总确认稳定的速度优势；其峰值显存为 422.25 MiB，相比两块的 668.50 MiB 更低。

p50 收益未全面改善 p95：16384 tokens 的两块 p95 为 2.9356 ms，高于整块 2.7139 ms；32768 tokens 为 5.0514 ms，高于整块 4.3448 ms。大 shape 的 wall/reset 收益也更小，不能按 event p50 的降幅直接推导 TTFT。

### 6.3 TP4：80 MiB 用整块，160 MiB 优先两块，320 MiB 可选四块

8192 tokens 的两块/四块流水相对整块分别慢 5.25% / 96.47%，四块甚至慢于 BF16。小块的启动与调度开销可能超过可隐藏的计算，需要 trace 确认具体占比。

16384 tokens 的两块与四块 p50 几乎相同，但四块 p95 为 1.7059 ms，两块为 1.0330 ms。两块适合优先考虑稳定延迟；四块额外峰值显存仅 189.13 MiB，低于两块的 322.25 MiB，可在显存优先时另行验证。

32768 tokens 的四块相对整块 p50 降低 13.42%，比两块进一步降低约 3.33%；p95 为 2.0707 ms，也低于两块的 2.1489 ms。额外峰值显存从整块 746.00 MiB 降至 362.25 MiB，降低约 51.44%。

### 6.4 TP8：已有小幅整体收益，流水增量收益有限

[16384,5120] 两块流水相对 BF16 的 p50 降低 5.78%，不能描述为完全无收益。相对整块 MXFP8 的增量为 1.19%，wall/reset 从 1.0410 ms 变为 1.0427 ms，基本持平；p95 则从 0.9787 ms 降至 0.9168 ms，降低约 6.32%。

完整路径对照差值为：

```text
分块串行 - 整块 = 1.1006 - 0.9223 = 0.1783 ms
分块串行 - 分块流水 = 1.1006 - 0.9113 = 0.1893 ms
整块 - 分块流水 = 0.9223 - 0.9113 = 0.0110 ms
```

流水相对串行的改善几乎抵消了分块新增成本。以上是组间 p50 差值，不是通过阶段计时测出的“隐藏通信时长”。流水峰值显存为 312.25 MiB，相比整块 361.00 MiB 降低 13.50%。

可能的限制包括：每 rank 仍处理完整输入的量化/打包成本；分块增加集合通信启动次数；后半段 AllGather 仍为 BF16。现有汇总表不能断言瓶颈一定是某一个算子、AIV 争用或某种拓扑。TP8 环境没有显式指定通信引擎，应结合对应 profiler 再判断。

## 7. 运行时配置与 benchmark 的区别

当前 [MXFP8 运行时](../vllm_ascend/distributed/device_communicators/mxfp8_all_reduce.py) 已支持：

| 配置 | 含义 |
| --- | --- |
| `enable` | 显式启用通信量化，默认 false |
| `quant_dtype` | `int8` 或 `mxfp8`，默认 int8 |
| `min_numel` | 是否进入量化路径，单位为元素数，默认 16777216，即 BF16 32 MiB |
| `pipeline_chunks` | MXFP8 固定块数 1/2/4；1 为整块，默认 1 |
| `pipeline_min_numel` | MXFP8 是否进入流水的独立门槛，默认使用 min_numel |

MXFP8 运行时仅允许在 A5 上初始化；每次调用检查组大小 2/4/8、BF16、shape、hidden 对齐、行分片及量化大小门槛。不满足调用量化条件时走普通 AllReduce；已满足量化条件但未满足流水门槛、行数不足或处于图捕获时，保持整块 MXFP8 路径。

异步分块当前限定 Eager 使用。代码没有额外的 prefill/decode 阶段过滤，而是按元数据、大小和捕获状态选路；图捕获时不进入异步分块流水。独立微基准不能自动证明运行时实机、模型 decode 图重放或流水入图已验收。

例如，TP4 可用以下候选配置对照“小消息整块、大消息两块”：

```json
{
  "quantized_all_reduce_config": {
    "enable": true,
    "quant_dtype": "mxfp8",
    "min_numel": 16777216,
    "pipeline_chunks": 2,
    "pipeline_min_numel": 83886080
  }
}
```

其中 83886080 元素对应 BF16 160 MiB / [16384,5120]。该示例依据现有采样点演示两级门槛，不宣称精确性能拐点，也不替代更小消息的量化收益测量。实际启动时合并到已有 `--additional-config`。

当前运行时不会自动按 TP/shape 在 2、4 块间切换；块数由配置固定。INT8 分块尚未接入运行时，`quant_dtype="int8"` 与非默认流水配置组合会被配置校验拒绝，不能使用上述参数开启 INT8 流水。

## 8. 复现实验与后续数据

已有 MXFP8 测试：

```bash
export HCCL_NPU_SOCKET_PORT_RANGE="61000-61050"
PYTHON=python3

for tp in 2 4 8; do
  "$PYTHON" -m torch.distributed.run --standalone --nproc-per-node="$tp" \
    benchmarks/benchmark_mxfp8_pipeline.py \
    --tokens 8192 16384 32768 --hidden-sizes 5120 --chunks 2 4 \
    --warmup 10 --iterations 50 --rounds 4 \
    --output "results/mxfp8_pipeline_tp${tp}.json"
done
```

TP8 当前回传只运行了 `--tokens 16384 --chunks 2`，不代表上面完整扫描已完成。INT8 使用相同设备/拓扑/环境独立测试：

```bash
# 先验证奇数行尾块和精度。
"$PYTHON" -m torch.distributed.run --standalone --nproc-per-node=2 \
  benchmarks/benchmark_int8_pipeline.py \
  --tokens 129 --hidden-sizes 5120 --chunks 2 4 --check-only

for tp in 2 4 8; do
  "$PYTHON" -m torch.distributed.run --standalone --nproc-per-node="$tp" \
    benchmarks/benchmark_int8_pipeline.py \
    --tokens 8192 16384 32768 --hidden-sizes 5120 --chunks 2 4 \
    --warmup 10 --iterations 50 --rounds 4 \
    --output "results/int8_pipeline_tp${tp}.json"
done
```

性能命令可添加 `--profile-dir results/方案名_traces`，在性能采样之外导出 profiler。MXFP8 另有 [一键对照时间轴](profile_mxfp8_pipeline.md)，可比较 BF16、整块和流水；阶段 CPU 标签用于定位，实际重叠看关联的 NPU kernel/HCCL 流。

后续优先补充：

| 数据 | 用途 |
| --- | --- |
| INT8 流水 TP2/4/8 的 p50/p95、显存、整数 SUM 和完整路径误差 | 判断共享 scale 流水收益，建立与 MXFP8 的同条件对照 |
