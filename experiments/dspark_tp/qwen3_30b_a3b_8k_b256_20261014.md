# Qwen3-30B-A3B：8K、256 并发 DSpark 验证（2026-10-14）

## 结论

在本轮 **TP8、随机输入 7168 token + 强制输出 1024 token、客户端并发 256** 的在线服务压测中，开启 DSpark 置信头没有收益：输出吞吐从无 DSpark 的 **381.19 token/s** 降到 **177.07 token/s（−53.55%）**。两组各 256/256 请求成功，8 条固定自然语言提示词的 greedy 输出逐字节一致。

本轮不能测得“物理缩 K”的真实收益：当前实现只在 `tensor_parallel_size <= 4` 时启用该路径；TP8 加上 `physical_k` 会回退到普通置信头路径。故没有再耗时运行一个名为 `physical`、实质与 `adaptive` 相同的 TP8 全量压测，也不把该配置冒充新功能的结果。要在 8K、总并发 256 下验证物理缩 K，需要另行选择 TP≤4 的部署拓扑（例如研究 DP2×TP4）或扩展 TP8 实现，并重新建立同拓扑基线。

## 容量、失败尝试与适用范围

- 最初沿用 `gpu-memory-utilization=0.86`：目标组 KV 容量 1,956,864 token，满 8K 理论并发 238.88；不足以驻留 256×8192，故在正式压测前停止，不计入结果。
- 上调至 `0.93` 后，目标组 KV 容量 2,144,384 token（261.77×8K）。首次压测没有显式固定温度，模型默认采样触发 top-p 排序，在约 204 路运行时额外申请约 600 MiB 并 OOM；该失败尝试不计入结果。随后把所有组的 benchmark 显式设为 `temperature=0`，两组正式结果均 256/256 成功。
- 同为 `0.93` 时，DSpark 组 KV 容量 1,905,024 token（232.55×8K），低于目标组。实际主压测的运行路数峰值只有 91，因此这轮主要不是 KV 容量打满，而是调度/计算路径的端到端表现；具体算子瓶颈仍需 profiling 才能下结论。
- `vllm_ascend/dynamic_spec.py` 将 `PHYSICAL_K_MAX_TP_SIZE` 设为 4；TP8 的 `physical_k` 通过 `ASCEND_AV_PHYSICAL_K_FALLBACK` 回退。此限制与 30B 权重本身无关。
